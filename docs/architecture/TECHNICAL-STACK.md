# DosaToppings Technical Stack

## Cost-first production architecture

The initial target is near-zero recurring infrastructure cost while maintaining server-side security for payments and staff operations. Free-tier limits are monitored; the design must allow paid upgrades without a rewrite.

## Services

- Cloudflare DNS/TLS/WAF/edge
- Cloudflare Pages for web applications/static assets
- Cloudflare Workers for server-side API/orchestration where suitable
- Supabase PostgreSQL for transactional application data and relational reporting
- Supabase Auth for customer/staff identity, email login and MFA where configured
- Supabase Storage where application media storage is appropriate
- Razorpay for online payment collection
- Resend for transactional email
- Google Drive for operational documents/exports, not transactional source-of-truth data
- GitHub for source control and deployment automation

## Security boundaries

The browser is an untrusted client. All final money, inventory, authorization, payment and reward decisions happen server-side.

Secrets are never committed to GitHub or shipped to browser JavaScript. Production secrets are configured through the selected provider's secret/environment management.

Admin and POS applications require authentication before privileged data or operations are available. Backend endpoints independently enforce authentication, staff status, role, permission and resource scope.

## Application surfaces

- `www.dosatoppings.in` — customer storefront
- `admin.dosatoppings.in` — authenticated administration
- `bill.dosatoppings.in` — authenticated POS/billing
- `api.dosatoppings.in` — backend API/edge functions as architecture evolves

Subdomains are not security boundaries.

## Payment architecture

Customer/POS client -> authoritative server pricing -> Razorpay order/payment -> server-side signature/webhook verification -> idempotent payment event -> order/payment state -> inventory and notification side effects.

Never trust a client-supplied final amount or payment-success flag.

## Email architecture

Order/payment/business events are generated by authoritative backend state. The backend persists a notification event, applies idempotency, sends through Resend, records provider response/status, and retries transient failures safely.

New-order notifications go to the active Super Admin email plus enabled configured operational recipients.

## Environment separation

Development/test and production must use separate credentials and data stores/projects where supported. No production secret belongs in source control.

## Migration rule

The existing static storefront remains the visual/content baseline until the replacement is validated. Existing products, copy, imagery and brand styling should be migrated deliberately.
